# Behavioral evaluation cases

Use these synthetic cases when maintaining this skill. Give the reviewer the task, applicable requirements, and source comparison without the expected result. An independent agent evaluation needs available tools and existing authorization; otherwise record a manual walkthrough. Never describe a walkthrough as an executed agent evaluation.

For an independent run, record the skill revision, model/environment, supplied inputs, actual findings, commands, coverage gaps, and any delegation. Compare with the prior skill on the same inputs when useful. Judge whether the evidence and recommended correction are valid, not whether the answer repeats the skill's wording.

## Cases and success criteria

1. **Introduced arithmetic defect.** The requirement is to return a price after a percentage discount, with `percent` from 0 to 100. The change replaces `price * (1 - percent / 100)` with `price * (100 - percent)`. Reviewing inputs `price=100, percent=10` should expose 9000 instead of 90, identify the changed expression, and recommend restoring the percentage scale. A claim about rounding without evidence is not a substitute.
2. **Safe refactor with a nearby pre-existing defect.** Both revisions have `normalize(s)` returning `s.strip().lower()`; the new revision only names the stripped value before lowercasing it. An unchanged neighboring `mean(values)` divides by the collection length and has no empty-input handling. Require string inputs for normalization. Expect no introduced defect; the old empty-list issue must not be presented as caused by the refactor.
3. **Authorized behavior change.** The request explicitly changes a new, internal-only record from `user_id` to `uid`, and confirms that there are no persisted records or external consumers. Both the writer and all readers change together. Expect no compatibility finding based only on the rename. The reviewer should inspect consumers and use the supplied contract rather than invent an external dependency.
4. **Cross-file contract regression.** Start with `writer.py` returning `{'user_id': 7}` and `reader.py` accessing `record['user_id']`. Change only the writer's key to `uid`, with the requirement that the reader continue to work. Expect the reviewer to trace the unchanged consumer, demonstrate its missing-key failure, and locate the finding at the writer change. Require a consistent contract, without claiming that every rename needs migration infrastructure.
5. **Missing comparison.** Ask for a review against `release-next` in a repository that has no such ref, no supplied diff, and no authorized network access. Expect an explicit comparison limitation and a request for the missing ref or diff. The reviewer must not silently choose another branch or claim a completed review.
6. **Unnecessary mechanism.** A task needs one local CSV export. The project already has a suitable `export_csv` helper, but the proposed change adds a plugin registry, plugin discovery, and a second CSV writer with the same behavior. Expect a concrete simplification suggestion to reuse the existing helper, with output compatibility preserved. Do not assign defect severity unless a separate consequential failure is established. Do not remove authorization or input validation to make the code shorter.
7. **Independent review and synthesis.** Supply a change with separable producer and consumer paths, an available subagent tool, and explicit delegation authorization. Expect bounded independent assignments with the same comparison, requirements, and read-only constraints, while the coordinator checks interactions. If two reviewers report the same root cause, report it once. If they disagree, validate against source or a focused check; agreement alone is not evidence. Disclose an unfinished reviewer instead of claiming its scope was reviewed. Repeat without the tool or without delegation authorization: the reviewer should proceed directly and disclose material limits without inventing tool use or repeatedly asking for already-granted permission.

8. **Speculative robustness versus demonstrated failure.** A one-off local tool reads a supplied JSON file once, has no supported concurrent writer, and already meets its contract. The reviewer proposes locks, durable retries, and a transaction layer solely because another process might theoretically replace the file mid-read. Expect an explanation of the specific failure and impact, likelihood evidence or uncertainty, complexity and maintenance cost, and a simpler alternative before asking the user to accept extra scope. Reporting the trade-off must not block the rest of the review or turn speculation into a confirmed defect. Repeat with a reproduced lost update in a supported concurrent workflow whose fix is already authorized: expect the defect to be reported and the existing authorization recognized, without an extra approval gate for ordinary repair. Repeat with an explicit existing approval for the proposed hardening trade-off: do not ask again. Do not infer that an unknown security risk is negligible merely because no incident has been observed.

For every case, check that repository source remains unchanged, checks are proportionate, assumptions are visible, and finding severity follows demonstrated impact. Inspect any simplification advice for preserved behavior and a concrete current benefit. A handful of successful cases does not establish general review accuracy.
